# GitHub setup (facilitators)

How to publish this starter, create the learner branches and lock down `main` so that every change goes through a pull request.

Do the steps in order. The branch rules come last on purpose: once they are on, nobody — including you — can push to `main` directly.

## Before you start

- **A GitHub plan that supports protected branches.** Branch rules are enforced on public repositories on every plan. On a **private** repository they need GitHub Pro, Team or Enterprise.
- **Admin access** to the repository.
- **Git**, the **.NET SDK** and, for the scripted option in step 5, the **GitHub CLI** (`gh`).
- **Never share your GitHub password or a token with anyone or any tool.** Git signs you in through your browser the first time you push.

## Step 1 — Check the solution on your machine

Follow "Getting started" in the [README](../README.md) as far as `dotnet test`. Everything should build and the tests should pass.

## Step 2 — Create the first migration

The starter ships without a migration so that it is generated by your installed EF Core version rather than written by hand. Create it once and commit it; every learner branch then starts with the `Users` table in place.

```
dotnet ef migrations add InitialCreate --project src/SelfServiceKiosk.Api --output-dir Data/Migrations
dotnet run --project src/SelfServiceKiosk.Api
```

In Swagger, try both login endpoints with the two test accounts from the README. Stop the API when both return a token.

## Step 3 — Create the repository and push

On GitHub, create a **new, empty** repository: no README, no .gitignore, no licence. Then, from the solution folder:

```
git init -b main
git add .
git commit -m "chore: initial solution structure with login API"
git remote add origin https://github.com/<owner>/<repository>.git
git push -u origin main
```

Open the **Actions** tab and wait for the **CI** workflow to finish with a green tick. It has to run once so that GitHub knows the `build-and-test` check exists.

## Step 4 — Create the 20 learner branches

Edit [`scripts/learners.txt`](../scripts/learners.txt): one learner per line. It ships with `learner-01` to `learner-20`; replace them with names or GitHub usernames if you prefer. Commit and push that change now, while `main` is still open.

Then run one of:

```
# PowerShell
.\scripts\create-learner-branches.ps1

# Git Bash, macOS or Linux
./scripts/create-learner-branches.sh
```

Each line becomes a branch called `learner/<name>`, created on GitHub from the tip of `main`. The script can be run again at any time; branches that already exist are skipped, so adding a 21st learner later is just a new line and another run. If GitHub refuses to create the new branch because the rules from step 5 are already on, switch the learner rule off, run the script, and switch it back on.

To do it by hand instead:

```
git fetch origin main
git push origin refs/remotes/origin/main:refs/heads/learner/<name>
```

## Step 5 — Apply the branch rules

Use **Option A or Option B, not both**. They give the same protection.

### What the rules do

| Rule | `main` | `learner/*` |
| --- | --- | --- |
| Direct pushes | Blocked for everyone, admins included | Blocked for everyone, admins included |
| Pull request required | Yes | Yes |
| Approvals required | 1 | 0 |
| Stale approvals dismissed on new commits | Yes | No |
| All review conversations resolved | Yes | No |
| `build-and-test` check must pass | Yes | Yes |
| Branch must be up to date before merging | Yes | No |
| Linear history (squash or rebase merges only) | Yes | No |
| Force pushes | Blocked | Blocked |
| Deleting the branch | Blocked | Blocked |

Learner branches need no approval so that learners can merge their own feature pull requests once the build is green; mentors review at the end of each phase. If mentors should approve every merge, change the approvals on `learner/*` to 1.

### Option A — scripted

Sign in once with `gh auth login`, then from inside the repository:

```
# PowerShell
.\scripts\apply-branch-rules.ps1

# Git Bash, macOS or Linux
./scripts/apply-branch-rules.sh
```

This creates two rulesets from the JSON files in [`scripts/github/`](../scripts/github/). Run it once; a second run fails because the names are already taken. Review or edit the result under **Settings → Rules → Rulesets**.

### Option B — by hand

Go to **Settings → Branches → Add classic branch protection rule** and create these two rules. Leave every option not listed below unticked.

**Rule 1 — Branch name pattern: `main`**

| Setting | Value |
| --- | --- |
| Require a pull request before merging | ✅ |
| ↳ Require approvals | ✅ — Required number of approvals: **1** |
| ↳ Dismiss stale pull request approvals when new commits are pushed | ✅ |
| ↳ Require review from Code Owners | ☐ (tick it after filling in `.github/CODEOWNERS`) |
| Require status checks to pass before merging | ✅ |
| ↳ Require branches to be up to date before merging | ✅ |
| ↳ Status checks that are required | Search for and add **`build-and-test`** |
| Require conversation resolution before merging | ✅ |
| Require linear history | ✅ |
| Do not allow bypassing the above settings | ✅ |
| Allow force pushes | ☐ |
| Allow deletions | ☐ |

**Rule 2 — Branch name pattern: `learner/*`**

| Setting | Value |
| --- | --- |
| Require a pull request before merging | ✅ |
| ↳ Require approvals | ☐ |
| Require status checks to pass before merging | ✅ |
| ↳ Require branches to be up to date before merging | ☐ |
| ↳ Status checks that are required | Search for and add **`build-and-test`** |
| Do not allow bypassing the above settings | ✅ |
| Allow force pushes | ☐ |
| Allow deletions | ☐ |

GitHub renames these options from time to time; if a label differs slightly, match on meaning.

## Step 6 — Repository settings and access

Under **Settings → General → Pull Requests**:

- ✅ Allow squash merging (required, because `main` enforces linear history)
- ✅ Automatically delete head branches (clears merged feature branches; protected branches are never deleted)

Under **Settings → Collaborators and teams**, add each learner with the **Write** role. Write access lets them push feature branches and open pull requests; the rules stop them pushing to `main` or to any `learner/*` branch.

## Step 7 — Confirm it works

```
git switch main
git commit --allow-empty -m "test: direct push should be rejected"
git push origin main
```

The push must be refused, with a message that mentions a protected branch or a repository rule violation. Then undo the test commit:

```
git reset --hard origin/main
```

## Things to know

- **You cannot approve your own pull request.** With one approval required on `main` and no bypass, changing the starter needs a second person with write access to approve. If you are the only facilitator, set the approvals on `main` to 0; a pull request and a green build are still required.
- **The check name must match.** The rules require a check called `build-and-test`, which is the job id in `.github/workflows/ci.yml`. If you rename the job, update the rule, or every pull request will wait forever.
- **Learner branches are not merged into `main`.** The brief makes this an individual project, so the 20 branches are 20 separate solutions. `main` stays as the starter.
- **Sending a fix to everyone.** Merge the fix into `main` through a pull request, then tell learners to follow "Picking up changes to the starter" in [CONTRIBUTING.md](../CONTRIBUTING.md).
- **One learner can open a pull request into another learner's branch.** The rules cannot tie a branch to a person on a standard repository. Every merge is recorded with who made it; if that is not enough, require 1 approval on `learner/*`.
